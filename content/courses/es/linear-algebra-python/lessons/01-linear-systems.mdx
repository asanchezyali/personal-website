Buena parte del álgebra lineal aplicada tiene su origen en un mismo problema: disponemos de varias
ecuaciones, todas lineales, y buscamos los valores que las satisfacen simultáneamente.

$$
\begin{aligned}
  x_1 + x_2 + x_3 &= 3\\
  x_1 - x_2 + 2x_3 &= 2\\
  x_2 + x_3 &= 2
\end{aligned}
$$

Presentado de este modo, el sistema parece exigir una sucesión de sustituciones. Expresado de otra
forma —una **matriz** $A$ con los coeficientes y un **vector** $\vec{b}$ con los términos
independientes— se convierte en una única pregunta:

$$A\vec{x} = \vec{b}$$

Esa pregunta admite una respuesta directa en NumPy.

## Planteamiento del sistema

Cada fila de $A$ corresponde a una ecuación, y el vector $\vec{b}$ recoge los términos situados al
otro lado de la igualdad:

```python
import numpy as np

A = np.array([[1,  1, 1],
              [1, -1, 2],
              [0,  1, 1]])
b = np.array([3, 2, 2])
```

Conviene observar que los coeficientes ausentes también ocupan posición: la tercera ecuación carece
de $x_1$, de modo que su primera entrada es un `0`. Una matriz no admite huecos.

## La resolución con NumPy

```python
x = np.linalg.solve(A, b)
# array([1., 1., 1.])
```

El resultado se obtiene en una sola llamada, pero merece la pena examinar qué ocurre internamente,
porque explica por qué esta es la instrucción adecuada y otras aparentemente equivalentes no lo son.

`solve` no calcula la inversa de $A$. Descompone la matriz en dos factores triangulares, $A = LU$, y
resuelve con ellos dos sistemas encadenados, cada uno inmediato por ser triangular. El coste es
$O(n^3)$, y la implementación descansa sobre LAPACK, la biblioteca de álgebra lineal que sostiene el
cómputo científico desde los años noventa.

El fundamento es sencillo: sumar a una ecuación un múltiplo de otra no altera el conjunto de

para leer la respuesta de forma directa.

## Verificación del resultado

Todo resultado numérico conviene comprobarlo. La sustitución es inmediata:

```python
np.allclose(A @ x, b)
# True
```

El operador `@` denota el producto matriz-vector. La comprobación emplea `allclose` y no `==`
deliberadamente: en aritmética de coma flotante el resultado exacto rara vez se obtiene de forma
exacta, y una comparación estricta devolvería `False` por un error del orden de $10^{-16}$ carente
de significado.

Con tres incógnitas la situación es análoga en una dimensión más: cada ecuación describe un
**plano**, y la solución es el punto en que los tres se cortan.

## ¿Cuándo no existe una solución única?

`solve` requiere que $A$ sea invertible. Si una fila es combinación de las restantes, la matriz
resulta **singular** y la función devuelve un error:

```python
C = np.array([[1,  1, 1],
              [1, -1, 2],
              [2,  0, 3]])

np.linalg.solve(C, np.array([3, 2, 1]))
# LinAlgError: Singular matrix
```

En este caso la tercera fila es la suma de las dos primeras, de modo que no aporta información
adicional: se trata de dos ecuaciones independientes presentadas como tres. El criterio que lo
determina es el **rango**, es decir, el número de filas genuinamente independientes:

```python
np.linalg.matrix_rank(C)
# 2
```

Cuando $\operatorname{rank}(A) < n$, el sistema admite cero o infinitas soluciones, nunca
exactamente una. Cuál de las dos posibilidades se materializa depende de $\vec{b}$: si resulta
compatible con la dependencia, las soluciones son infinitas; si la contradice, no existe ninguna.

El estado final resulta revelador: en el bloque correspondiente a $A$ aparece una fila de ceros, lo
que confirma que la tercera ecuación no aportaba información nueva. Si su término independiente
queda distinto de cero, el sistema exige que $0 = \text{algo}$, condición imposible, y por eso no
admite solución.

Para estas situaciones NumPy ofrece `lstsq`, que proporciona la solución de mínimos cuadrados —
aquella que minimiza el error residual — incluso cuando `solve` no puede operar:

```python
x, residuos, rango, sv = np.linalg.lstsq(C, np.array([3, 2, 1]), rcond=None)
```

## `solve` frente a `inv`

Para resolver $A\vec{x} = \vec{b}$ conviene emplear `solve` y evitar `inv(A) @ b`.

```python
x = np.linalg.solve(A, b)      # recomendado
x = np.linalg.inv(A) @ b       # desaconsejado
```

Ambas expresiones producen resultados prácticamente idénticos, pero la segunda realiza más trabajo
—calcular la inversa completa resulta más costoso que resolver el sistema— y acumula mayor error
numérico. Además, la inversa en sí misma rara vez es necesaria: lo que se requiere es su *efecto*
sobre un vector, que es precisamente lo que `solve` proporciona.
