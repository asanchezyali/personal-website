A large part of applied linear algebra originates in a single problem: we have several equations, all
linear, and we are looking for the values that satisfy them simultaneously.

$$
\begin{aligned}
  x_1 + x_2 + x_3 &= 3\\
  x_1 - x_2 + 2x_3 &= 2\\
  x_2 + x_3 &= 2
\end{aligned}
$$

Presented this way, the system appears to call for a sequence of substitutions. Expressed
differently — as a **matrix** $A$ holding the coefficients and a **vector** $\vec{b}$ holding the
constant terms — it becomes a single question:

$$A\vec{x} = \vec{b}$$

That question has a direct answer in NumPy.

## Setting up the system

Each row of $A$ corresponds to one equation, and the vector $\vec{b}$ collects the terms on the
other side of the equality:

```python
import numpy as np

A = np.array([[1,  1, 1],
              [1, -1, 2],
              [0,  1, 1]])
b = np.array([3, 2, 2])
```

It is worth noting that absent coefficients still occupy a position: the third equation has no
$x_1$, so its first entry is a `0`. A matrix admits no gaps.

## Solving with NumPy

```python
x = np.linalg.solve(A, b)
# array([1., 1., 1.])
```

The result comes from a single call, but the internals deserve examination, because they explain why
this is the appropriate instruction and why other apparently equivalent ones are not.

`solve` does not compute the inverse of $A$. It decomposes the matrix into two triangular factors,
$A = LU$, and uses them to solve two chained systems, each immediate by virtue of being triangular.
The cost is $O(n^3)$, and the implementation rests on LAPACK, the linear algebra library that has
underpinned scientific computing since the nineties.

The underlying principle is straightforward: adding a multiple of one equation to another does not
alter the solution set of the system. Repeating that operation leads to a formulation simple enough
for the answer to be read off directly.

## Verifying the result

Every numerical result warrants checking. Substitution is immediate:

```python
np.allclose(A @ x, b)
# True
```

The `@` operator denotes the matrix-vector product. The check uses `allclose` rather than `==`
deliberately: in floating-point arithmetic the exact result is rarely obtained exactly, and a strict
comparison would return `False` over an error on the order of $10^{-16}$ that carries no meaning.

## When is there no unique solution?

`solve` requires $A$ to be invertible. If one row is a combination of the others, the matrix is
**singular** and the function returns an error:

```python
C = np.array([[1,  1, 1],
              [1, -1, 2],
              [2,  0, 3]])

np.linalg.solve(C, np.array([3, 2, 1]))
# LinAlgError: Singular matrix
```

Here the third row is the sum of the first two, so it contributes no additional information: two
independent equations presented as three. The criterion that settles this is the **rank**, the
number of genuinely independent rows:

```python
np.linalg.matrix_rank(C)
# 2
```

When $\operatorname{rank}(A) < n$, the system admits either zero or infinitely many solutions, never
exactly one. Which of the two occurs depends on $\vec{b}$: if it is compatible with the dependency,
the solutions are infinite; if it contradicts it, none exists.

The final state is revealing: a row of zeros appears in the block corresponding to $A$, confirming
that the third equation carried no new information. If its constant term ends up non-zero, the
system requires that $0 = \text{something}$, an impossible condition, and therefore admits no
solution.

For these situations NumPy provides `lstsq`, which returns the least-squares solution — the one that
minimises the residual error — even when `solve` cannot operate:

```python
x, residuals, rank, sv = np.linalg.lstsq(C, np.array([3, 2, 1]), rcond=None)
```

## `solve` versus `inv`

To solve $A\vec{x} = \vec{b}$, `solve` is the appropriate choice and `inv(A) @ b` should be avoided.

```python
x = np.linalg.solve(A, b)      # recommended
x = np.linalg.inv(A) @ b       # discouraged
```

Both expressions produce practically identical results, but the second performs more work —
computing the full inverse is costlier than solving the system — and accumulates greater numerical
error. Moreover, the inverse itself is rarely required: what is needed is its *effect* on a vector,
which is precisely what `solve` provides.
